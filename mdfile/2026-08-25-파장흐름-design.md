> 기존 `mdfile/집가_설계정리.md` §7.1 "파장 흐름"을 확정하고, 그 과정에서 §4 게임 모듈 규격까지 개정한 설계 문서

## 0. 용어

논의 중 "세션"이 두 가지 의미로 쓰였다. 이 문서에서는 아래로 고정한다.

| 용어 | 뜻 | 수명 |
|---|---|---|
| **방** (Room) | 술자리 하나. QR로 모인 인원의 단위 | TTL 2시간, 활동 시 연장 |
| **세션** (Session) | 한 번 열리는 미니게임 3판 묶음 | 5분 내외 |
| **판** (Round) | 미니게임 1회 | `timeLimitSec` |

한 방 안에서 세션이 30~60분 주기로 여러 번 열린다.

---

## 1. 배경

기존 설계에서 §7.1이 비어 있던 이유는 **게임 파트와 파장 파트의 시간 모델이 다르기 때문**이다.

게임 파트는 "방 = 동기화된 단위"를 전제로 짜여 있다. 시드를 한꺼번에 뿌리고, 서버가 지정한 시각에 전원이 동시 출발하고, 전원 제출을 기다려 순위를 낸다. 반면 파장은 비동기다. 술자리는 한꺼번에 끝나지 않는다. 한 명이 먼저 일어나고, 마지막 사람은 한참 뒤에 나간다.

이 문서는 그 불일치를 다음과 같이 봉합한다.

- **개인 귀가**와 **방장 파장 선언**을 둘 다 지원한다
- 귀가는 세션 경계에서만 일어나므로, 세션 내부는 기존의 동기화 모델을 그대로 유지한다
- 벌칙을 카카오T 연동에 통합해, 파장이 앱의 부록이 아니라 핵심 루프가 되게 한다

---

## 2. 핵심 전환 — 벌칙이 곧 귀가다

**벌칙 = 카카오T가 실행되고 방에서 나가는 것.**

이 하나로 여러 미결 항목이 동시에 닫힌다.

- 기존 §7.2의 "벌칙 내용을 앱이 제시할지"가 사라진다. 벌칙이 앱 기능 그 자체다
- 앱 이름이 그대로 벌칙 대사가 된다 — 꼴찌에게 "집 가"
- 기존 §6 카카오T 연동이 부록에서 핵심 루프로 올라온다. 진입점은 둘(벌칙/자발)이고 딥링크 모듈은 하나를 공유한다

### 2.1 절대평가를 택한 이유와 그 효과

벌칙 대상은 **순위가 아니라 절대 기준선**으로 정한다.

이로 인해 파장 곡선이 규칙에서 저절로 나온다. 술이 오를수록 점수가 떨어지므로 **초반에는 거의 아무도 걸리지 않다가 후반에 벌칙이 늘어난다.** 상대평가(꼴찌)였다면 매 세션 무조건 한 명이 나가서 인위적이었을 것이다.

부수 효과로 1등도 기준 미달이면 벌칙이고, 전원이 미달이면 전원이 간다. 순위 발표는 재미 요소로 남되, 벌칙 판정은 순위와 완전히 분리된 축이 된다.

## 3. §A — 게임 모듈 규격 (기존 §4 전면 교체)

절대평가는 "누가 더 잘했나"가 아니라 "얼마나 잘해야 통과인가"를 요구한다. 기존 계약에는 그 정보가 없었다.

문제는 게임마다 점수 스케일이 다르다는 점이다. 구구단 스피드전은 20문제 만점이고 카드 짝맞추기는 10쌍이다. 기준선을 게임 개발자 재량에 맡기면 어떤 게임은 아무도 안 걸리고 어떤 게임은 전원이 걸린다. 여러 사람이 나눠서 만든다는 전제에서는 거의 확실히 터진다.

**해결: 게임이 0~100으로 정규화해서 반환하고, 기준선은 앱이 공통으로 갖는다.**

### 3.1 게임이 앱으로부터 받는 값 (변경 없음)

```
seed          : number   // 랜덤 시드. 모든 플레이어가 동일한 값을 받음
timeLimitSec  : number   // 이 게임의 제한시간
```

> ⚠️ **시드는 반드시 사용할 것.** 카드 배치·문제 순서 등 모든 무작위 요소는 이 시드에서 파생시켜야 한다. 폰마다 다른 문제가 나오면 분쟁이 생긴다.

### 3.2 게임이 앱에 돌려주는 값 (개정)

```
normalizedScore : number   // 0~100. 항상 높을수록 좋음
score           : number   // 원점수. 화면 표시 전용 ("18/20문제")
tiebreakMs      : number   // 걸린 시간(ms). 동점 판별용 — 항상 작을수록 유리
finished        : boolean  // 완주 여부
```

### 3.3 `higherIsBetter`를 제거한다

이번 개정의 핵심 소득이다.

기존 §4.3은 `higherIsBetter`를 두고 *"이게 없으면 앱이 누가 꼴찌인지 판단할 수 없다"*고 경고했다. 그런데 `normalizedScore`를 **항상 높을수록 좋다**고 규정하면 방향 문제가 계약 밖으로 밀려난다. 시간 기반 게임은 게임 쪽에서 뒤집어 반환하면 되고, 앱은 방향을 알 필요가 없다.

앱이 쓰는 규칙이 두 줄로 줄어든다.

- **순위** — `normalizedScore` 내림차순, 동점이면 `tiebreakMs` 오름차순
- **벌칙** — 세션 평균 `normalizedScore < 40`

### 3.4 게임 정보 (게임당 한 번 선언 · 개정)

```
id           : string    // 고유 식별자
name         : string    // 표시 이름
emoji        : string    // 아이콘
desc         : string    // 한 줄 설명
timeLimitSec : number    // 기본 제한시간
```

`higherIsBetter` 제거. 나머지는 기존과 동일.

### 3.5 정규화 가이드

계약에서 유일하게 판단이 필요한 부분이므로 명시한다.

> **원칙** — 이 게임을 잘하는 사람이 대략 100, 전혀 못 한 사람이 대략 0이 되도록 매핑하고, 마지막에 0~100으로 clamp 한다.

| 게임 유형 | 매핑 |
|---|---|
| 개수형 (구구단 20문제) | `맞힌 수 / 전체 수 × 100` |
| 시간형 (카드 짝맞추기) | 목표 시간을 잡고 `목표 / 걸린시간 × 100`, clamp |
| 실패형 (실수 횟수) | `(1 − 실수/허용치) × 100`, clamp |

### 3.6 기준선

```
PENALTY_THRESHOLD = 40
```

앱 전역 상수 하나로 시작한다. 게임별로 기준선을 다르게 두는 순간 3.5의 정규화가 무의미해진다. 밸런스가 어긋나면 게임의 정규화 식을 고치는 것이 맞지, 기준선을 흔들 자리가 아니다.

방장이 난이도를 조절하는 기능은 필요해지면 그때 얹는다.

### 3.7 게임 개발자 체크리스트

- [ ] 모든 무작위 요소를 `seed`에서 파생시켰는가
- [ ] `normalizedScore`가 0~100 범위이고, 높을수록 좋은 방향인가
- [ ] 시간·실패 기반 게임이라면 뒤집어서 반환했는가
- [ ] 제한시간이 끝나면 스스로 종료하고 점수를 반환하는가
- [ ] 시간 초과 시에도 **그때까지의 정규화 점수**를 반환하는가 (0점 처리 금지)
- [ ] 네트워크 코드가 없는가

## 4. §B — 벌칙 · 강퇴 · 재입장

### 4.1 판정

```
세션 점수 = 3판 normalizedScore의 평균
벌칙 대상 = 세션 점수 < 40 인 모든 참가자
```

순위와 무관하다. 인원 제한도 없다 — 0명일 수도, 전원일 수도 있다.

**판마다 판정하지 않는 이유**는 4.5(세션 단위 판정)에 있다.

### 4.2 벌칙 실행 시퀀스

```
세션 종합 결과 발표
   │
   ├─ 통과자 → 대기 화면 (누가 걸렸는지 같이 표시)
   │
   └─ 벌칙자 → 3 · 2 · 1 카운트다운
                    │
                    ▼
              카카오T 딥링크 실행
                    │  (미설치 시 스토어 폴백)
                    ▼
              귀가 완료 화면
```

카운트다운이 도는 동안 다른 사람 화면에도 누가 걸렸는지 같이 뜬다. 벌칙은 본인만 보면 재미가 없다.

**판정과 강퇴는 한 트랜잭션에서 끝난다.** 서버의 `end_session`이 평균을 계산하는 그 자리에서 미달자를 방에서 제거하므로, 클라이언트는 응답의 `penalized` 플래그를 보고 연출만 재생한다. 방 제거를 별도로 호출하지 않는다.

> ⚠️ **자발적 귀가는 다르다.** "집에 갈래"는 클라이언트가 `leave_room()`을 직접 호출하므로 **응답을 받은 뒤에 딥링크를 열어야 한다.** 딥링크를 먼저 쏘면 앱이 백그라운드로 내려가면서 요청이 유실될 수 있다.

### 4.3 자발적 귀가

세션 사이(종합 결과 화면 · 로비)에만 **"집에 갈래"** 버튼이 노출된다.

누르면 벌칙과 **완전히 동일한 경로**를 탄다 — 서버 제거 커밋 후 카카오T 실행. 카운트다운만 없다. 딥링크 모듈도 제거 로직도 하나만 만들면 되고, 다른 것은 트리거뿐이다.

**세션 진행 중에는 버튼이 없다.** 3판은 끝까지 간다. 세션 하나가 5분 남짓이라 실제로 불편하지 않고, 도중 이탈로 평균 계산이 깨지는 경우도 막힌다.

### 4.4 재입장

딥링크는 콜백이 없어 **그 사람이 실제로 택시를 탔는지 앱은 알 수 없다.** 벌칙만 받고 자리에 그대로 앉아 있는 경우가 반드시 생긴다.

재입장을 QR 재스캔으로 만들면 안 된다. 방장 폰을 다시 찾아가야 하는데 취한 상태에서는 실패한다.

> 나간 사람의 폰에 방 코드를 로컬 저장하고, 첫 화면에 **"아직 안 갈래"** 버튼을 띄운다. 한 번 누르면 원래 방으로 복귀한다.

- 방이 아직 살아있는 동안만 유효하다. 소멸했으면 안내 후 새로 파도록 유도한다
- 세션이 진행 중이면 다음 세션부터 참여한다 (4.7)
- 재입장 횟수에 제한을 두지 않는다

### 4.5 세션 단위 판정을 택한 이유

판마다 판정하면 1판에서 40 미만이 나온 사람이 즉시 강퇴되어 2·3판을 못 한다. 남은 두 판은 인원이 줄어든 채로 돌아가고, 세션 중간에 카카오T가 떠서 흐름이 끊긴다.

세션 끝에 한 번만 판정하면 전부 해결된다.

- 한 판 삐끗해도 남은 두 판에서 만회할 수 있다
- 강퇴는 세션당 최대 한 번, 그것도 마지막에만 일어난다
- 3판을 묶은 덕에 운의 영향이 줄어 40점 기준이 더 정확해진다

### 4.6 방장 승계

방장도 벌칙에서 예외가 아니다.

> 방장이 나가면 **남은 사람 중 가장 먼저 입장한 사람**이 자동 승계한다.

서버가 입장 순서만 알면 되므로 판정이 단순하고 결정적이다. 재입장해도 방장은 돌려받지 않는다 — 왔다 갔다 하면 방이 흔들린다.

### 4.7 세션 진행 중 입장·재입장

세션이 이미 시작된 뒤 들어온 사람(신규 QR 스캔, 재입장 모두)은 **진행 중인 세션에 끼지 않는다.** 게임 3개와 시드가 이미 배포됐고 판이 돌아가는 중이다.

"다음 게임 대기 중" 화면을 띄우고 다음 세션부터 참여시킨다. 관전 기능은 구현 부담 대비 가치가 낮아 넣지 않는다.

### 4.8 방 소멸

**인원이 0이 되면 방 삭제.** 전원 벌칙이든, 하나씩 다 빠졌든, 경로와 무관하게 같은 규칙이다. 다시 하려면 새로 판다.

40점 기준에서 전원 미달은 드물게 일어나므로, 이 경계를 위해 특별한 장치를 두지 않는다.

### 4.9 게임 중 이탈이 저절로 흡수된다

기존 §2의 이탈자 규칙 — *제한시간 내 미제출 시 자동 꼴찌 + 최하점*.

최하점이면 `normalizedScore = 0`이고, 3판 중 하나가 0이면 평균이 크게 떨어져 자연스럽게 40 미만으로 간다. **별도 규칙 없이 4.1 하나로 처리된다.** 기존의 "튄 사람 전원 벌칙" 조항도 절대평가 아래서 자동으로 성립한다.

앱을 떠난 상태라 딥링크는 못 받지만 그건 자연스럽다 — 이미 나간 사람이다. 네트워크가 잠깐 끊겼던 것뿐이라면 4.4로 돌아온다.

### 4.10 부분 점수

기존 §2의 "앱이 살아있으면 그때까지의 점수 인정" 조항은 그대로 유지된다. 3.7 체크리스트의 "시간 초과 시에도 그때까지의 정규화 점수를 반환" 항목이 이를 계약 수준에서 강제한다.

## 5. §C — 방 생명주기와 세션 주기

### 5.1 TTL + 활동 연장

방을 시간으로 만료시킨다. **Presence를 방의 생사 기준으로 삼으면 안 되기 때문이다.** 폰이 절전으로 들어가거나 술집 LTE가 끊기면 Presence는 그 사람을 나간 것으로 본다. 접속 상태에 방의 수명을 걸면 멀쩡한 방이 죽는다. TTL은 그런 흔들림에 영향받지 않는다.

방이 오래 살아 있는 비용도 사실상 없다. Supabase는 접속 기준으로 과금하며, 활동 없는 행 하나는 무료다.

### 5.2 확정 값

| 항목 | 값 |
|---|---|
| 방 TTL | 2시간 |
| 세션 주기 | 방장 설정, 30분 ~ 1시간 |
| 주기 기본값 | 30분 |
| 주기 변경 | 방장이 로비에서 언제든 |
| 첫 세션 | 방 생성 직후 바로 가능 (타이머는 첫 세션 종료 후부터) |
| 세션 최소 인원 | 2명 ※ 제안값 — 아래 참고 |

> ※ 최소 인원은 이번 논의에서 명시되지 않아 제안값으로 넣었다. 1명이 남아 혼자 3판을 하고 40 미만이면 강퇴되어 방이 소멸하는데, 논리적으로는 일관되나 화면상 어색하다. 2명 미만이면 세션 시작 버튼을 비활성화한다.

### 5.3 시간은 트리거가 아니라 알림이다

> ⚠️ **주기가 찼다고 서버가 게임을 자동 시작해서는 안 된다.**

벌칙이 강퇴이기 때문이다. 화장실에 간 사람, 담배 피우러 나간 사람의 폰에서 게임이 혼자 시작되고 끝난다. `normalizedScore = 0` → 평균 하락 → 벌칙 → 강퇴. 아무 잘못 없이 집에 가라는 소리를 듣고, 그것이 30분마다 반복된다.

```
주기 도달 → 로비에 "게임할 시간!" 배지
                │
                └─ 방장이 시작을 누름 → 세션 시작
```

사람이 한 명 개입하는 것만으로 오발동이 전부 사라진다. 강퇴가 되돌리기 번거로운 액션인 이상 자동화하면 안 되는 자리다.

### 5.4 연장 규칙

```
expires_at = now() + 2시간
```

갱신 트리거는 셋이다.

- 세션 종료 (점수 집계 완료 시점)
- 새 참가자 입장
- 강퇴자 재입장

주기 타이머는 **마지막 세션 종료 시점부터** 다시 센다. 고정 격자가 아니라 슬라이딩이다. 방장이 늦게 시작해도 다음 주기가 밀려서 따라온다.

### 5.5 서버 구현

`rooms` 테이블에 `expires_at` 컬럼 하나면 된다.

정리는 **지연 방식**을 쓴다. 별도 배치 없이, 입장·재입장 요청이 들어올 때 `expires_at`을 확인해 지났으면 거절하고 그 자리에서 방을 정리한다. 만료된 방이 DB에 잠깐 남는 것은 문제가 되지 않으며, cron을 안 붙이는 만큼 관리 대상이 줄어든다. "서버 관리 인력이 없다"는 기존 §3.3의 전제와 맞는다.

### 5.6 로비 표시

- **다음 세션까지 남은 시간** — 없으면 사람들이 폰을 계속 확인한다
- 주기가 차면 배지 + 방장 화면의 시작 버튼 강조
- 방장에게만 보이는 주기 설정 (30 / 45 / 60분)

TTL 만료 경고는 넣지 않는다. 2시간 동안 세션도 입장도 없었다면 이미 다 집에 간 자리다.

## 6. §D — 세션은 랜덤 3판

### 6.1 방장은 "시작"만 누른다

방장이 게임을 고르면 **자기가 잘하는 게임을 고른다.** 시드로 공정성을 맞춰놓고(기존 §2) 게임 선택에서 편파가 들어오면 앞의 노력이 무의미해진다.

```
로비에서 방장이 시작
        │
        ▼
게임 3개 공개 (슬롯머신 연출)
        │
        ▼
1판 → 결과 → 2판 → 결과 → 3판
        │
        ▼
세션 종합 결과 + 벌칙 판정
```

방장이 누르는 버튼은 "시작" 하나뿐이다. 무엇을 할지는 아무도 모른다.

### 6.2 게임 선정도 시드에서 파생

세션이 열릴 때 서버가 **세션 시드**를 발급하고, 여기서 두 가지를 파생시킨다.

- 어떤 게임 3개가 뽑히는가 (세션 내 중복 없이)
- 각 판의 게임 시드

시드 하나에서 전부 나오므로 서버가 추가로 보낼 것이 없고, "왜 하필 저 게임이냐"는 시비도 원천 차단된다. 아무도 개입할 수 없는 값이기 때문이다.

> ⚠️ **게임 풀에 최소 3개가 필요하다.** 현재 후보는 구구단 스피드전과 카드 짝맞추기 둘뿐이므로 하나는 더 확보해야 이 구조가 성립한다.

### 6.3 판 사이 결과 화면

각 판이 끝나면 그 판의 순위만 짧게 보여주고, **누적 평균은 마지막까지 숨긴다.** 3판째까지 긴장이 유지되고, 종합 발표 한 번에 벌칙까지 몰아서 터뜨릴 수 있다.

## 7. §E — 문구 체계

어미 하나로 두 경로가 갈린다.

| 상황 | 문구 | 말하는 주체 | 어조 |
|---|---|---|---|
| 벌칙 (타의) | **집 가** | 앱이 나에게 | 명령형 |
| 자발 귀가 (자의) | **집에 갈래** | 내가 앱에게 | 의지형 |
| 재입장 (자의) | **아직 안 갈래** | 내가 앱에게 | 의지형 (부정) |

"집 가"는 앱 이름이자 벌칙 대사다. 자발적 귀가에까지 같은 문구를 쓰면 그 무게가 희석된다.

자발적인 두 버튼은 `-ㄹ래`로 짝을 이루고 방향만 반대다. 벌칙만 명령형으로 혼자 떨어져 나오므로, **문구만 봐도 내 의지인지 앱이 시킨 것인지 즉시 구분된다.**
