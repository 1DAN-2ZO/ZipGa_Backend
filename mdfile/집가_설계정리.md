# 집 가 — 설계 정리

> 술자리에서 다 같이 한 방에 들어가 미니게임을 하고, 마지막엔 카카오T로 택시를 잡아주는 앱
>
> 작성일: 2026-08-25 · 상태: 파장 흐름 확정 (§7.1 종료)
>
> 파장·벌칙·세션 구조의 상세 근거는 [`docs/superpowers/specs/2026-08-25-파장흐름-design.md`](../docs/superpowers/specs/2026-08-25-파장흐름-design.md) 참조

---

## 1. 프로젝트 개요

**한 줄 정의** — 술자리 인원이 QR로 한 방에 모여 미니게임으로 순위를 가리고, 파장 때 택시까지 이어주는 모바일 앱.

**목표 지점** — 실제 출시 (앱스토어 / 플레이스토어)

**팀 구조** — 미니게임은 여러 사람이 나눠서 개발. 따라서 **게임 모듈 규격을 먼저 확정**하는 것이 최우선.

---

## 2. 확정된 결정 사항

| 항목 | 결정 | 비고 |
|---|---|---|
| 앱 형태 | React Native | 실제 스토어 배포 목표 |
| 게임 진행 방식 | 각자 폰에서 독립 실행, **최종 점수만 취합** | 실시간 동기화 불필요 |
| 서버 | 관리형 BaaS (**Supabase 권장**) | ⚠️ 최종 확정 전 |
| 입장 방식 | 방장이 QR 표시 → 나머지가 스캔 | 딥링크 `jipga://room/{코드}` |
| 공평성 보장 | 방장이 **시드(seed)** 배포 → 모든 폰이 동일 문제 생성 | 필수, 사후 추가 불가 |
| 시작 동기화 | 서버가 **시작 시각** 지정 → 전원 카운트다운 후 동시 출발 | |
| 게임 선택 | 방장은 **시작만** 누름 → 시드에서 **랜덤 3판** 추첨 | 방장 편파 차단 |
| 세션 구조 | 한 세션 = **3판 연속** | 판수는 조정 여지 |
| 세션 주기 | 방장 설정 **30분 ~ 1시간** (기본 30분) | 시간은 알림만, 시작은 사람이 |
| 방 수명 | **TTL 2시간**, 활동 시 연장 | 인원 0 → 방 삭제 |
| 순위 산정 | `normalizedScore` 순, 동점 시 **걸린 시간** | |
| 벌칙 판정 | **절대평가** — 3판 평균 `normalizedScore < 40` | 순위와 무관 |
| 벌칙 내용 | **카카오T 실행 + 방에서 강퇴** | 3·2·1 카운트다운 후 |
| 자발 귀가 | **"집에 갈래"** — 세션 사이에만, 벌칙과 동일 경로 | 카운트다운 없음 |
| 재입장 | **"아직 안 갈래"** — 로컬 저장된 방 코드로 복귀 | 횟수 제한 없음 |
| 방장 승계 | 방장 이탈 시 **남은 사람 중 최초 입장자** | 재입장해도 반환 안 함 |
| 이탈자 처리 | 제한시간 내 미제출 시 **자동 꼴찌 + 최하점** | 절대평가로 자동 흡수 |
| 다중 이탈 | 튄 사람 **전원 벌칙** | 별도 규칙 불필요 |
| 부분 점수 | 앱이 살아있으면 그때까지의 점수 인정 | 완전 이탈자만 최하점 |
| 택시 연동 | 카카오T 단독 | 미설치 시 스토어 폴백 |

## 3. 아키텍처 판단 근거

### 3.1 왜 실시간 동기화를 안 하는가

당초엔 서버가 게임 진행을 심판하는 구조(권위 서버)를 검토했으나, **각 폰에서 같은 게임을 따로 돌리고 점수만 모으는 방식**으로 결정됨.

이 결정의 파급 효과:

- 게임 도중 네트워크 통신이 **전혀 발생하지 않음**
- 서버가 다루는 이벤트가 적음 — 방 생성 / 입장 / 재입장 / 세션 시작 신호 / 점수 제출 / 방 제거 / 방장 승계
- 한 판당 오가는 메시지가 **수십 개 수준** (실시간 방식 대비 1/20 이하)
- 게임 개발자가 네트워크를 몰라도 됨 → **협업 난이도 대폭 하락**

> 파장 흐름(§7)을 확정하면서 이벤트가 4종에서 7종으로 늘었으나, 전부 **사람이 버튼을 누를 때만** 발생하는 저빈도 이벤트다. 게임 중 무통신이라는 전제는 그대로다.

### 3.2 서버 비용 검토

> 논의 배경: "서버 비용을 줄이고 싶다", "서버 관리할 사람이 없다"

**QR 코드는 비용과 무관** — QR은 방 코드를 옆 사람 폰으로 옮기는 UI 수단일 뿐, 방을 유지하는 주체는 여전히 서버. 다만 취객 대상 UX로는 코드 입력보다 QR이 확실히 낫다.

비용을 실제로 줄이는 선택지는 세 가지였다:

| 방식 | 서버비 | 문제점 |
|---|---|---|
| 방장 폰이 서버 (P2P) | 거의 0 | 술집 LTE 환경에서 연결 실패 잦음 → TURN 중계 서버 필요 → 결국 비용 발생. 방장이 앱 내리면 방 사망 |
| 블루투스 / 근거리 통신 | 0 | 인터넷 불필요는 장점이나, iOS·안드로이드 혼재 시 구현 난이도 급상승. RN에서 네이티브 모듈 직접 작업 필요 |
| 관리형 BaaS | 사실상 0 | **채택** |

**결론** — 현 설계의 트래픽 규모에서는 무료 구간을 벗어나기 어렵다. 비용 절감을 이유로 P2P나 블루투스를 택하면 구현 난이도만 몇 배로 오르고 아끼는 돈은 미미하다.

참고 수치:

- **Supabase** 무료 — 동시접속 200, 월 200만 메시지 · Pro($25) — 동시접속 500, 월 500만 메시지, 초과분 100만 메시지당 $2.50
- **Cloudflare Durable Objects** 무료 — 일 10만 요청 · 유료 — 100만 요청당 $0.15

### 3.3 왜 Supabase인가

- **Presence 기능 내장** — 방에 누가 들어와 있는지 실시간 표시가 거의 공짜로 구현됨 (로비 화면 직결)
- 무료 구간이 초기 규모를 충분히 커버
- 추후 역대 랭킹 · 친구 목록 · 로그인 확장이 자연스러움
- 서버 관리 인력 불필요 — 계정 생성 후 SDK 연결이 전부. 서버 재시작 · 패치 · 모니터링 작업 없음

> Firebase도 후보였으나, 실시간 DB 쪽이 신규 프로젝트에서 다소 레거시 취급을 받는 점을 고려해 Supabase 우선.

## 4. 게임 모듈 규격 ★

> **다른 개발자가 미니게임을 붙일 때 지켜야 할 계약.**
> 이것만 지키면 네트워크도, 다른 플레이어도 신경 쓸 필요 없음. 혼자 하는 미니게임 하나 만드는 것과 동일.

### 4.1 게임이 앱으로부터 받는 값

```
seed          : number   // 랜덤 시드. 모든 플레이어가 동일한 값을 받음
timeLimitSec  : number   // 이 게임의 제한시간
```

> ⚠️ **시드는 반드시 사용할 것.** 카드 배치·문제 순서 등 모든 무작위 요소는 이 시드에서 파생시켜야 한다.
> 폰마다 다른 문제가 나오면 "쟤는 쉬운 거 나왔다" 분쟁이 생긴다.

### 4.2 게임이 앱에 돌려주는 값

```
normalizedScore : number   // 0~100. 항상 높을수록 좋음
score           : number   // 원점수. 화면 표시 전용 ("18/20문제")
tiebreakMs      : number   // 걸린 시간(ms). 동점 판별용 — 항상 작을수록 유리
finished        : boolean  // 끝까지 완주했는지 (중도 이탈 시 false)
```

> ⚠️ **벌칙 판정에 쓰이는 건 `normalizedScore` 하나뿐이다.** `score`는 화면에 예쁘게 보여주기 위한 값일 뿐 계산에 쓰이지 않는다.

### 4.3 게임 정보 (게임당 한 번 선언)

```
id           : string    // 고유 식별자
name         : string    // 표시 이름
emoji        : string    // 아이콘
desc         : string    // 한 줄 설명
timeLimitSec : number    // 기본 제한시간
```

> `higherIsBetter`는 **제거되었다.** `normalizedScore`가 "항상 높을수록 좋음"으로 고정이므로
> 방향 문제가 계약 밖으로 밀려났다. 시간 기반 게임은 게임 쪽에서 뒤집어 반환하면 된다.

### 4.4 정규화 가이드

계약에서 유일하게 판단이 필요한 부분이다.

> **원칙** — 이 게임을 잘하는 사람이 대략 100, 전혀 못 한 사람이 대략 0이 되도록 매핑하고,
> 마지막에 0~100으로 clamp 한다.

| 게임 유형 | 매핑 |
|---|---|
| 개수형 (구구단 20문제) | `맞힌 수 / 전체 수 × 100` |
| 시간형 (카드 짝맞추기) | 목표 시간을 잡고 `목표 / 걸린시간 × 100`, clamp |
| 실패형 (실수 횟수) | `(1 − 실수/허용치) × 100`, clamp |

기준선은 앱 전역 상수 하나다 — `PENALTY_THRESHOLD = 40`. 게임별로 기준선을 다르게 두면 정규화가 무의미해지므로, 밸런스가 어긋나면 **게임의 정규화 식을 고친다.**

### 4.5 게임 개발자 체크리스트

- [ ] 모든 무작위 요소를 `seed`에서 파생시켰는가
- [ ] `normalizedScore`가 0~100 범위이고, 높을수록 좋은 방향인가
- [ ] 시간·실패 기반 게임이라면 뒤집어서 반환했는가
- [ ] 제한시간이 끝나면 스스로 종료하고 점수를 반환하는가
- [ ] 시간 초과 시에도 **그때까지의 정규화 점수**를 반환하는가 (0점 처리 금지)
- [ ] 네트워크 코드가 없는가 (있으면 안 됨)

### 4.6 게임 후보

논의 중 언급된 것들 — 전부 "느긋한" 성격. 밀리초 단위 실시간 판정이 필요한 게임은 현 구조상 제외.

- 구구단 스피드전
- 카드 짝맞추기
- (추가 예정)

> ⚠️ **최소 3개가 필요하다.** 한 세션이 랜덤 3판이므로 풀에 3개가 없으면 구조가 성립하지 않는다.
> 현재 2개이므로 하나는 반드시 더 확보해야 한다.

## 5. 화면 흐름

```
앱 실행
  │
  ├─ 방 만들기 ──────→ QR 표시 ─┐
  ├─ QR 스캔 ───────────────────┤
  └─ "아직 안 갈래" (재입장) ────┤
                                 ▼
                    로비 (참가자 목록 · 다음 세션까지 남은 시간)
                                 │  주기 도달 → "게임할 시간!" 배지
                                 │  방장이 시작 (선택 없음)
                                 ▼
                       게임 3개 공개 (시드에서 랜덤 추첨)
                                 │
                    ┌────────────┤
                    │            ▼
                    │   카운트다운 3·2·1  ← 서버 지정 시각에 전원 동시
                    │            ▼
                    │   게임 (각자 폰에서 독립 실행)
                    │            ▼
                    │   점수 제출 → 판 결과 (그 판 순위만)
                    └──── × 3 ───┘
                                 ▼
                    세션 종합 결과 (3판 평균 최초 공개)
                                 │
                   ┌─────────────┴─────────────┐
             평균 ≥ 40                     평균 < 40
                   │                           │
                   ▼                           ▼
             대기 화면                  "집 가" 3·2·1
          (누가 걸렸나 표시)                    │
                   │                           ▼
                   │              서버 제거 커밋 → 카카오T 실행
                   ▼
             로비 (다음 세션 대기)
                   │
                   └─ "집에 갈래" → 서버 제거 커밋 → 카카오T 실행
```

**판 사이의 누적 평균은 숨긴다.** 3판째까지 긴장을 유지하고, 종합 발표 한 번에 벌칙까지 몰아서 터뜨리기 위함이다.

## 6. 카카오T 연동

카카오T는 외부 앱을 위한 **공식 딥링크 API가 공개되어 있지 않음.** 따라서:

1. 앱 스킴으로 카카오T 실행 시도
2. 실패(미설치) 시 → 앱스토어 / 플레이스토어로 유도

> 안드로이드 패키지: `com.kakao.taxi` · iOS App Store ID: `981110422`

⚠️ 공식 API가 아니므로 카카오 측 변경에 영향을 받을 수 있다. 출시 전 실기기 검증 필수.

### 6.1 진입점은 둘, 모듈은 하나

| 진입점 | 트리거 | 카운트다운 |
|---|---|---|
| 벌칙 | 3판 평균 < 40 | 3·2·1 있음 |
| 자발 귀가 | "집에 갈래" 버튼 | 없음 |

경로가 완전히 동일하므로 **딥링크 모듈도 방 제거 로직도 하나만 만든다.** 다른 것은 트리거뿐이다.

### 6.2 순서를 지킬 것

```
서버에 방 제거 커밋 → 응답 확인 → 딥링크 실행
```

딥링크를 먼저 쏘면 앱이 백그라운드로 내려가면서 제거 요청이 유실될 수 있다.

### 6.3 콜백이 없다는 사실이 설계를 결정한다

딥링크는 단방향이라 **그 사람이 실제로 택시를 탔는지 앱은 영영 알 수 없다.** 벌칙만 받고 자리에 그대로 앉아 있는 경우가 반드시 생긴다. 재입장("아직 안 갈래")이 필수인 이유가 이것이다.

## 7. 파장 흐름 ✅ 확정

상세 근거는 [파장 흐름 설계 문서](../docs/superpowers/specs/2026-08-25-파장흐름-design.md) 참조. 요지만 옮긴다.

### 7.1 벌칙이 곧 귀가다

**벌칙 = 카카오T가 실행되고 방에서 나가는 것.** 이 하나로 "벌칙 내용"과 "라운드 구조" 미결이 함께 닫혔다.

- 앱 이름이 그대로 벌칙 대사가 된다 — 기준 미달자에게 "집 가"
- 카카오T 연동이 부록에서 핵심 루프로 올라온다

### 7.2 절대평가가 파장 곡선을 만든다

순위가 아니라 **3판 평균 40점**이라는 절대 기준으로 판정한다. 술이 오를수록 점수가 떨어지므로 **초반엔 거의 아무도 안 걸리다가 후반에 벌칙이 늘어난다.** 상대평가(꼴찌)였다면 매 세션 무조건 한 명이 나가서 인위적이었을 것이다.

1등도 미달이면 벌칙이고, 전원 미달이면 전원이 간다. 인원이 0이 되면 방은 삭제되고, 다시 하려면 새로 판다.

### 7.3 왜 세션 단위로 판정하는가

판마다 판정하면 1판에서 걸린 사람이 2·3판을 못 하고, 세션 중간에 카카오T가 떠서 흐름이 끊긴다. 세션 끝에 한 번만 판정하면 만회 기회가 생기고, 강퇴는 세션당 최대 한 번 마지막에만 일어난다.

### 7.4 시간은 게임을 시작시키지 않는다

주기가 찼다고 서버가 자동으로 게임을 띄우면 **화장실 간 사람이 0점으로 강퇴된다.** 주기는 로비 배지로만 알리고, 시작은 반드시 방장이 누른다.

### 7.5 문구 체계

| 상황 | 문구 | 어조 |
|---|---|---|
| 벌칙 (타의) | **집 가** | 명령형 — 앱이 나에게 |
| 자발 귀가 (자의) | **집에 갈래** | 의지형 — 내가 앱에게 |
| 재입장 (자의) | **아직 안 갈래** | 의지형 (부정) |

자발적인 두 버튼이 `-ㄹ래`로 짝을 이루고 방향만 반대다. 벌칙만 명령형으로 떨어져 나오므로 문구만 봐도 내 의지인지 앱이 시킨 것인지 구분된다.

## 8. 아직 정하지 않은 것

- **누적 통계 / 역대 랭킹** — 방이 소멸하면 기록도 사라지는 현 설계에서 별도 저장이 필요한지
- **역할 분담 및 일정**
